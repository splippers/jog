Chapter 1: The big picture
Chapter 1

The big picture

Brume is the server side of a portable imaging appliance. It is an Ubuntu laptop running stock FOG, an isolated DHCP/TFTP imaging network, and a Chromium kiosk that points at this portal.

Client PCsPXEBrume laptopHTTP/NFSFOG images

The four pieces

  • Brume configures the laptop: Ubuntu, FOG install, DHCP/TFTP, firewall, kiosk, wizard and portal.
  • FOG stays stock. It stores hosts, images, tasks and multicast sessions.
  • JOS/Brume Agent runtime is the client boot/runtime path that talks to FOG with the stock FOS userland.
  • GIFT checks a Windows golden image before capture so stale images are rebuilt, not cloned.

Three separate planes

  • Imaging: USB Ethernet only, isolated DHCP/TFTP/PXE.
  • Management: Wi-Fi or onboard Ethernet reaches FOG web, updates and this portal.
  • VM lab: libvirt NAT gives Windows VMs internet without touching the imaging link.
Rule: Brume configures the laptop. JOS/Brume Agent runtime runs on, or builds for, the machine being imaged. FOG remains an unmodified upstream server.
Chapter 2

Boot and kiosk

The appliance starts from Ubuntu 26.04 live server. Autoinstall lays down the base system; the wizard and installers add the imaging stack; LightDM starts the operator UI without a desktop shell.

Ubuntu autoinstallthenmist-install-wizardthenFOG + kiosk

What the installer builds

  • /opt/mist (or /opt/mist compat): this repository and its scripts.
  • /opt/fogproject and /opt/fog: stock FOG source and install tree.
  • /tftpboot: signed shim, GRUB, kernel, initrd and modules for JOS.
  • /etc/mist/mist.env (or /etc/mist/mist.env compat): live role configuration.

How the kiosk starts

  • LightDM autologs in mist.
  • The mist-kiosk session runs /usr/local/bin/chromium-mist.sh (or compat wrapper).
  • Chromium opens this portal first, then FOG management and the status page.
  • Brume_CHROMIUM_RESTART=1 relaunches Chromium if it exits.
No GNOME Shell is used. The kiosk depends on X11, LightDM, Chromium and this portal only.
Chapter 3

Networks and safety

Brume has deliberately separate network roles. Mixing them would put a DHCP server on the wrong link, which is the main hazard this appliance is designed to prevent.

Interface roles

  • Imaging: validated USB Ethernet, currently enx34298f79151f, static 10.99.0.1/24.
  • Backhaul: Wi-Fi wlp0s20f3, default route for updates and FOG web access.
  • VM NAT: virbr0 on 192.168.122.0/24, forwarded through Wi-Fi.
  • Brumetry: hidden management hotspot/API, never an imaging DHCP server.

The safety chain

  1. The wizard only allows a USB-attached, non-wireless Ethernet NIC for imaging.
  2. mist-dhcp-guard.py probes for a foreign DHCP server before enabling DHCP.
  3. dnsmasq binds only to that NIC, with no-dhcp-interface for every other physical NIC.
  4. The portal reports armed only when all of those checks agree.
The onboard NIC eno1 is disabled. libvirt's virbr0 runs its own VM DHCP service; it is not the imaging DHCP server.
Chapter 4

Control portal

This page is a thin browser UI over a loopback JSON API. It keeps secrets on the server and asks for sudo only when an action changes the system.

Browser panelJSON127.0.0.1:8088readsFOG API / helper

Read views

  • Overview, hosts, images, VM fleet, ISO lists and logs load without a password prompt.
  • FOG tokens are read from /etc/mist/fog-api.env by the service, never sent to the browser.
  • VM lists use /api/vm/view through passwordless local sudo.

Privileged actions

  • Create, delete, restart, network changes, VM actions and checkpoints open the sudo modal.
  • Credentials go only to the loopback API and are used once through mist-portal-network.sh.
  • The helper allowlists commands and binds the API to 127.0.0.1.
If a panel shows an error instead of data, check Overview for service health and FOG API state before changing anything.
Chapter 5

FOG server

FOG is the inventory, image store and task scheduler. Brume does not fork it; the portal just drives its REST API with a dedicated API-only user.

Services

  • apache2: FOG web management.
  • mariadb: host, image and task database.
  • tftpd-hpa: PXE boot files.
  • nfs-server: image transport for JOS clients.
  • FOGMulticastManager and FOGScheduler: multicast and task timing.

Objects you manage

  • Hosts: machines identified by MAC address.
  • Images: stored OS captures, normally zstd format for Linux/JOS workflows.
  • Tasks: deploy, capture and multicast jobs.
  • Sessions: multicast rooms with a port and client count.
FOG DHCP stays disabled. DHCP/TFTP are provided by Brume's isolated dnsmasq instance, not by FOG.
Chapter 6

PXE and Brume Agent/JOS

Imaged machines do not boot a FOG kernel directly. They follow a signed UEFI chain into the JOS/Brume Agent runtime, which then runs the stock FOS userland against FOG.

UEFI PXEshimGRUBsigned kernelJOS/Brume Agent initrdFOS userlandFOG

Boot chain

  • Microsoft-signed shimx64.efi is served first.
  • GRUB loads a Canonical-signed kernel, the JOS/Brume Agent initrd and signed modules.
  • The boot menu offers deploy/capture, registration, system info, debug and memtest.
  • mist-stage-jos-boot.sh (or compat) stages everything under /tftpboot.

Why JOS/Brume Agent runtime exists

  • Stock FOS needs its own kernel and cannot boot with Dell Secure Boot enforcing keys.
  • JOS/Brume Agent keeps FOS userland but uses a signed Ubuntu kernel and matching modules.
  • mist-doctor.sh (or compat) verifies the staged chain and flags kernel drift.
  • The client fetches FOG files by HTTP and image data by NFS.
Memtest needs Secure Boot off. iPXE is omitted because it is unsigned and cannot be the first stage.
Chapter 7

Windows VM workshop

The VM panels build a local Windows 11 golden-image candidate with Secure Boot, TPM 2.0 and internet through libvirt NAT.

Build VMthenFleetthenConsolethenCheckpoints

Build choices

  • ISOs are discovered from /var/lib/libvirt/isos/; Windows and VirtIO media are separated automatically.
  • SATA disk and e1000e NIC are the safe defaults for Windows setup.
  • VirtIO ISO stays attached for later driver installation.
  • Secure Boot and TPM 2.0 satisfy Windows 11 requirements.

Workshop loop

  1. Build and start the VM from the Build VM panel.
  2. Open the VNC display from the Console panel and install Windows.
  3. Install drivers, join the domain if required and apply updates.
  4. Create a checkpoint before risky changes or sysprep.
  5. Run GIFT, then capture the VM as a FOG image.
VM internet uses virbr0 and the Wi-Fi default route. It never uses the imaging USB NIC.
Chapter 8

Imaging workflow

Once a golden image is ready, FOG captures it and can deploy it back to machines over the isolated imaging link.

Prepare

  1. Register the host MAC in the Hosts panel.
  2. Create or select the image record in the Images panel.
  3. Boot the client from PXE and choose the JOS menu entry.
  4. Run GIFT before capture if the image is Windows.

Run

  • Capture: reads the client disk and writes a FOG image.
  • Deploy: restores an image onto the selected host.
  • Multicast: sends one image stream to a session of clients.
  • Active and recent task state appears in Overview and Imaging tasks.
Create image records with the correct format. A blank format can cause FOS restore scripts to do nothing.
Chapter 9

Golden image gate

GIFT is the freshness check that stops an old, patched-by-hand image from becoming the new fleet standard.

What GIFT checks

  • Patch support and update freshness.
  • Installed software and unexpected changes.
  • Domain membership and activation state.
  • BitLocker state and escrow readiness.

What happens next

  1. Boot the candidate Windows image offline from the imaging network.
  2. Run gift.ps1 and save the HTML report.
  3. Fix every FAIL and review WARN results.
  4. Capture the image only after the gate passes.
The post-capture Windows payload handles drivers, hostname, domain or hybrid join, AD groups and BitLocker escrow. Check the Drivers panel before rollout.
Chapter 10

Operations and scaling

Day-to-day operation is service health, logs and safe expansion. Never solve capacity by putting two DHCP servers on one broadcast domain.

Daily operations

  • Use System and logs to restart services and read journal output.
  • Rotate FOG API tokens with sudo /usr/local/sbin/mist-fog-api-init.sh --force (or compat).
  • Restage JOS/Brume Agent boot files after a kernel update.
  • Re-run the safety check after any NIC or network change.

Scaling patterns

  • One Brume per imaging switch or table, with non-overlapping subnets.
  • One FOG primary with storage nodes for fan-out.
  • Edge Brume nodes syncing /images from a primary.
  • Better switch fabric or 10GbE before adding more heads.
Only one DHCP server may answer on an imaging segment. Multicast sessions should also stay one per VLAN.
Chapter 11

Troubleshooting

Most failures map to one of a few layers. Start at the layer that changed last, then move outward.

Quick diagnosis

  • Safety review: imaging NIC missing, wireless, or not USB Ethernet; reattach and re-run the check.
  • Portal offline: check mist-imaging-api and http://127.0.0.1:8088/api/session.
  • FOG error: check service health and API tokens; do not assume the list is empty.
  • VM no internet: check virbr0, libvirt NAT rules and the Wi-Fi default route.

Boot and kiosk failures

  • PXE fails: check /tftpboot, dnsmasq bootfile, and staged JOS/Brume Agent files.
  • Secure Boot rejects boot: confirm shim, signed kernel and GRUB staging.
  • Kiosk fails: check lightdm --show-config, LightDM logs and /tmp/mist-kiosk-mist.log (or compat log).
  • NIC disappeared: check kernel USB disconnect messages and physical cabling.
Do not bypass safety to keep imaging running. A missing imaging NIC is a stop condition, not a reason to enable DHCP on another interface.
